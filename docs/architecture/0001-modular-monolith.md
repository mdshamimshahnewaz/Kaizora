# ADR 0001: API-first modular monolith

Status: accepted for foundation, based on the user's requested architecture.

## Context
Project delivery and client operations share people, time, replacement history and
billing. TaskBridge's reference docs describe mutable snapshots and active-only
historical lookups. Those behaviors must not be replicated as requirements.

## Decision
Use Django 5.2 LTS, DRF, React/TypeScript and PostgreSQL. One backend deployment,
one database, explicit domain boundaries. Vite is a development/build tool, not
our production server. Django Admin is an internal operator surface.

Web/mobile -> HTTP JSON `/api/v1/` -> DRF adapters -> module interfaces/use cases
-> owning module's models -> PostgreSQL.

Inside Django, modules call Python interfaces. No network hop is needed. Public
interfaces expose typed commands/queries and DTOs. Domain implementations stay
private. Each write must have an explicit transaction owner. Foreign keys are
allowed when justified; a relationship never grants another module write ownership.
Cross-domain orchestration belongs in an explicit use case with documented dependencies.

Module contracts live in feature specs. `interfaces.py` is the only allowed
cross-module code import. The architecture checker catches ordinary static imports;
it does not detect raw SQL, dynamic imports or model access through Django's registry.
Those remain review responsibilities. Django framework configuration and migrations
may reference model labels; domain code may not use them to bypass interfaces.

## API and mobile
OpenAPI is generated by drf-spectacular and committed under `docs/api/`. React's
client types are generated from it. Version paths rather than maintaining separate
web/mobile APIs. Schema changes require regeneration and compatibility review.

Foundation auth: Django Admin sessions and default-deny DRF SessionAuthentication.
Application login/logout and CSRF-protected session mutations were implemented by
[feature 0002](../specs/0002-session-shell/spec.md). No mobile token endpoint exists.
Organisation membership and object permissions require a separate identity spec
before business APIs ship. Native mobile authentication needs OAuth/OIDC Authorization
Code + PKCE (or an explicitly reviewed alternative), refresh/revocation and secure
device storage before mobile authentication ships.
No credentials in frontend environment variables. No permissive CORS default.
Local React proxies `/api` to Django; production should use a same-origin reverse proxy.

## Consequences
Fast transactions and fewer infrastructure components, but deployment is shared.
Extraction is possible, not automatic: a future service needs owned storage,
remote contracts, consistency/retry semantics, authentication and a migration plan.
Notifications/integrations may be extraction candidates later. Do not add a generic
message bus, outbox or Redis/Celery until a spec needs durable asynchronous work.

## Data decisions
Custom UUID user model exists before initial migration. Other entities and tenant
schema remain unimplemented pending identity/organization specs. Legacy IDs must
be mapped explicitly during a future migration; no TaskBridge data is imported.
PostgreSQL is mandatory for runtime and database tests; no SQLite fallback.
